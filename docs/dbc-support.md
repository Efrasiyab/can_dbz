# DBC support profile

The initial DBC adapter is deliberately incremental. By default, unsupported statements fail with a diagnostic and source line/column. Call `parseWithOptions` with `preserve_unsupported_statements = true` to retain unsupported statements, including multi-line ones, in `Document.dbc.opaque_statements`; the default `parse` API remains strict.

## Export requirements

`dbc.write` omits the document name, extensions, and unknown `dbc` metadata because DBC has no matching fields. Use `dbc.writeWithDiagnostics` to receive warnings for those omissions. Document value tables are exported as `VAL_TABLE_`, and signals that reference one also get per-signal `VAL_` values, so reuse by name is not retained on re-import. Sections are written in DBC grammar order, signals with several receivers use comma-separated names, and line breaks in descriptions are written literally. Export fails with `error.UnsupportedConstruct` for constructs the writer cannot safely encode; diagnostics identify each blocker.

- More than one bus, or a bus not named `can0` (or with a description, protocol or attributes).
- Descriptions on the bus (`CM_` comments are supported for the document, nodes, messages and signals).
- More than one transmitter on a message, or message receivers.
- Attributes other than bounded message-scoped integers, including bus, node, signal, and document assignments.
- Names that are not valid DBC identifiers.

Missing signal `minimum`/`maximum` do not block export; they are written as `[0|0]`.

Malformed supported declarations (such as `BO_`, `SG_`, `CM_ BU_`, `CM_ BO_`, `CM_ SG_`, `VAL_TABLE_`, `VFrameFormat`, `VAL_`, `SG_MUL_VAL_`, and `SIG_VALTYPE_`) remain errors even when preservation is enabled. Export also rejects metadata that the current DBC profile cannot represent (for example bus descriptions and multiple buses). The adapter is not yet a general-purpose DBC converter.
